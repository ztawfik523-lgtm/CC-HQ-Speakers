## What the mod is

CC:HQ Speakers upgrades the normal ComputerCraft `speaker` into a better programmable audio peripheral.

Lua decides whether audio is music, effects, alarms, speech, notifications, ambience, soundboards, or something else. Java exposes technical capabilities rather than application roles.

The normal `computercraft:speaker` remains the product surface.

## Explain behavior first

For finite files, explain the system like this before talking about classes or packets:

```text
ComputerCraft has a file
    -> HQ Speakers imports it into server-owned media storage
    -> the server starts and owns the playback timeline
    -> a relevant Minecraft client is told where playback currently is
    -> that client asks for only small encoded pieces around the current point
    -> later M1G decodes those pieces into positional sound
```

Do not lead user explanations with packet/class/executor names.

## What M1F changed

Old modern path:

```text
server asset
-> server pushes complete file
-> client writes .part
-> client renames complete .media file
-> old complete-file decoder opens it
```

Current M1F path:

```text
server asset
-> authoritative STATE + encoded anchor
-> client range request
-> bounded off-thread server read
-> range response
-> bounded client RAM window
```

The modern client no longer needs the whole asset or a persistent client song file before future decoding can begin.

## Removed prototype/transition pieces

Removed from the modern finite path:

- `audioPlayStaged()`;
- direct staged finite playback;
- `HQFiniteMediaChunkPacket`;
- `HQFiniteMediaEndPacket`;
- tick-thread whole-file finite sending;
- client `.part/.media` accumulation;

`audioPlayStaged()` was our own prototype function, not inherited compatibility. Do not restore it.

## Current finite protocol

Protocol version: `5`.

Range request identifies:

```text
source + asset + generation + offset + bounded length
```

Range response identifies:

```text
source + asset + generation + offset + bytes
```

Authoritative STATE also carries:

- canonical position/duration/state/volume/loop;
- server-selected `anchorOffset`;
- corresponding `anchorTime`.

The client waits for STATE before requesting any encoded bytes. It does not assume byte zero from BEGIN.

## Current M1F bounds

Implementation tuning values:

- one range: max 128 KiB;
- one active client encoded window: 512 KiB;
- per player: max 4 outstanding range reads;
- per player: max 512 KiB outstanding range bytes;
- server range IO: 2 threads;
- server range IO queue: 64.

These values are safety/tuning choices, not product-level permanent guarantees.

## Server safety/lifetime behavior

An accepted range read retains the MediaAsset before leaving the server thread.

The range worker performs the bounded file read off-thread.

Before sending the result, the server rechecks:

- active playback;
- source/generation/asset identity;
- player connection;
- dimension/range relevance;
- response bounds.

Stale completions are discarded.

Server shutdown stops/drains range workers before the MediaAsset store can close/delete its files. Queued cancelled jobs release their temporary asset references. Close can be retried if worker shutdown cannot complete the first time.

## Client RAM contract

`FiniteRangeWindow` distinguishes:

- data already available;
- valid data not arrived yet;
- actual asset EOF;
- stale/cancelled window.

This exact distinction matters for M1G: a temporary network gap must not be exposed to the MP3 decoder as permanent EOF.

The window supports arbitrary encoded re-anchors and discards obsolete history instead of becoming a client song cache.

## MP3/WAV boundary for M1G

Current MP3 analysis already has coarse encoded seek points. M1F can transport from the server-selected MP3 anchor.

Current WAV analysis records the WAV audio-data start, not the final direct PCM layout/time-to-byte mapping. M1G must extend WAV metadata with the layout needed for exact range selection and conversion.

This does **not** require a new transport protocol. M1F already supports arbitrary encoded offsets.

MP3 Layer III reservoir pre-roll is also M1G. The transport already allows earlier anchors; M1G decides the actual codec-safe pre-roll policy.

## What M1G must build next

M1G owns:

```text
bounded encoded M1F window
    -> progressive decoder/converter worker
    -> bounded mono PCM queue
    -> positional Minecraft/OpenAL renderer
```

Core formats:

- MP3/MPEG Layer III;
- common WAV.

M1G must prove:

- temporary encoded starvation is not EOF;
- progressive MP3 decode;
- MP3 seek/rejoin pre-roll;
- common WAV integer/float conversion;
- mono remains mono, stereo downmixes to mono, >2 channels reject;
- bounded PCM memory;
- decoder cancellation;
- no sound-thread network/disk/decode blocking;
- actual audible positional playback.

Do not repair the old JavaSound/mp3spi file bridge instead.

## M1H remains separate

M1F validates current relevance on requests and again before sending asynchronous results.

M1H still owns complete listener lifecycle:

- discover a player who enters range after playback started;
- proactive leave-range client cancellation;
- return/rejoin at current server time;
- dimension/world/resource-reload lifecycle;
- underrun refill/rejoin;
- VS2 moving-speaker lifecycle.

Do not claim M1F already solved M1H.
